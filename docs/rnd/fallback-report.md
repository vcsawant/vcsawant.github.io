# Fallback assets for the WebGL scenes (Phase 7 R&D)

Non-WebGL fallback assets for the two WebGL scenes — a seamless looping VP9
WebM plus AVIF/JPEG posters each — generated by a committed, re-runnable
pipeline.

## Deliverables

| file                        | bytes     | size      | notes                                  |
| --------------------------- | --------- | --------- | -------------------------------------- |
| `public/fallback/hero.webm` | 1,223,245 | 1.22 MB   | VP9, 1280x720, 24 fps, 15.0 s, no audio |
| `public/fallback/hero.avif` | 34,528    | 33.7 KiB  | poster: knight fully resolved          |
| `public/fallback/hero.jpg`  | 90,252    | 88.1 KiB  | JPEG fallback of the same frame        |
| `public/fallback/graph.webm`| 172,669   | 169 KiB   | VP9, 1524x720, 24 fps, 12.4 s, no audio |
| `public/fallback/graph.avif`| 4,706     | 4.6 KiB   | poster: resting constellation          |
| `public/fallback/graph.jpg` | 26,996    | 26.4 KiB  | JPEG fallback of the same frame        |

All within budget: WebM <= 1.5 MB (under both the 1.5e6-byte and 1.5-MiB
readings), >= 720p, 6-15 s, single VP9 video stream, no audio track (`-an`;
confirmed via `ffmpeg -i`). Posters: AVIF <= 60 KB, JPEG <= 120 KB.

## Pipeline usage

```sh
npm ci && npx playwright install chromium   # once
node scripts/generate-fallbacks.mjs         # builds dist/ if missing, writes public/fallback/*
# options: --scene hero|graph   regenerate one scene only
#          --keep-frames        keep .fallback-frames/ PNG sequences for inspection
```

The script serves `dist/` itself on `127.0.0.1:4531`, drives headless Chromium
(`--enable-unsafe-swiftshader` so WebGL2 works without a GPU), captures PNG
frame sequences, and encodes with `ffmpeg` (required on PATH; fails fast if
absent).

### Deterministic capture

Playwright's fake clock (`page.clock.install`) replaces `Date`,
`performance.now`, `requestAnimationFrame` and `requestIdleCallback`, so
`clock.runFor()` advances the scenes exactly and rasterizer speed is
irrelevant. Two hard-won details:

- **`clock.pauseAt` is mandatory.** An installed clock still *flows with real
  time*; only after `pauseAt` does time move exclusively via `runFor`. Without
  it, each screenshot's ~100-300 ms of real latency silently advanced the
  scene between steps and the first capture ran ~3.5x too fast with garbled
  phases.
- **Integer stepping must not drift.** `runFor` takes integer ms; stepping a
  naive `round(1000/24) = 42 ms` per frame drifts 120 ms per 15 s cycle. The
  capture loop advances to `round(i * 1000/24)` cumulatively, keeping total
  error < 1 ms.

Hydration under a paused clock (client:idle / client:visible) is pumped with
`runFor(100)` until the scene's debug object reports frames. The graph page is
scrolled explicitly (`#skills` anchor navigation does not reliably scroll under
a fake clock) so the `client:visible` island's IntersectionObserver fires.

Capture-time CSS (injected by the script, not in app code): the hero's
`.hero-copy` overlay is hidden (the video replaces only the canvas layer
behind the text), and `.graph-box` border/radius are stripped (the video will
live inside the box, which supplies its own chrome).

## Loop techniques

### Hero — phase-aligned full cycle + head crossfade

The morph cycle (knight → "VS" → graph wireframe) is exactly
`3 x (2600 + 2400) = 15000 ms` periodic, but the low-amplitude `uTime` swirl /
idle drift is not. So:

1. With `?heroT0=0` (see hook below) the morph phase *is* the virtual clock.
   Capture waits for the next multiple of 15000 ms (log: "capture starts at
   virtual t=135000") and grabs **390 frames** at 24 fps: one 360-frame cycle
   plus 30 frames (1.25 s) of overhang.
2. ffmpeg `xfade` blends the overhang (input 0, frames 360-389) into the head
   (input 1, frames 0-359) over the first 1.25 s. Both sides of the blend share
   the same morph phase — the fade only hides the tiny non-periodic drift
   residual, and it lands in the knight dwell where that residual is minimal.
3. Loop point: output frame 359 is capture frame 359; output frame 0 is capture
   frame 360 — *consecutive captured frames*, hence seamless by construction.

### Graph — ping-pong (forward + reversed)

The graph drifts monotonically (~0.05 rad/s; a revolution takes ~2 min), so a
crossfade would ghost two rotations. Instead: capture **150 frames (6.25 s)**
forward, then append the time-reversed interior (frames 148..1 — first and
last reversed frames dropped so no frame plays twice in a row). Output is 298
frames / 12.42 s. Frame N flows into frame 0 exactly (they are adjacent source
frames), and at ~0.05 rad/s the direction reversal at the midpoint reads as a
gentle sway rather than a bounce.

## Exact ffmpeg invocations

Hero WebM (two-pass; the CRF search landed at 58):

```sh
ffmpeg -y \
  -framerate 24 -start_number 360 -i .fallback-frames/hero/f%04d.png \
  -framerate 24 -start_number 0   -i .fallback-frames/hero/f%04d.png \
  -filter_complex "[0:v]crop=1280:720,setpts=PTS-STARTPTS[a];\
[1:v]crop=1280:720,trim=end_frame=360,setpts=PTS-STARTPTS[b];\
[a][b]xfade=transition=fade:duration=1.25:offset=0[v]" \
  -map "[v]" -c:v libvpx-vp9 -b:v 0 -crf 58 -row-mt 1 -pix_fmt yuv420p -an \
  -pass 1 -passlogfile .fallback-frames/vp9log -f null /dev/null
# ...same again with -pass 2 and the output path public/fallback/hero.webm
```

Graph WebM (two-pass; CRF 40 fit on the first try):

```sh
ffmpeg -y -framerate 24 -start_number 0 -i .fallback-frames/graph/f%04d.png \
  -filter_complex "[0:v]scale=-2:720,split[f][g];\
[g]reverse,trim=start_frame=1:end_frame=149,setpts=PTS-STARTPTS[r];\
[f][r]concat=n=2:v=1[v]" \
  -map "[v]" -c:v libvpx-vp9 -b:v 0 -crf 40 -row-mt 1 -pix_fmt yuv420p -an \
  -pass 1 -passlogfile .fallback-frames/vp9log -f null /dev/null
# ...same again with -pass 2 and public/fallback/graph.webm
```

Posters (budget loops landed at AVIF crf 30, JPEG q 5 for both scenes):

```sh
# hero: capture frame f0031 (t = 1300 ms — mid-dwell, knight fully resolved)
ffmpeg -y -i .fallback-frames/hero/f0031.png -vf crop=1280:720 -frames:v 1 \
  -pix_fmt yuv420p -c:v libsvtav1 -crf 30 -preset 4 -f avif public/fallback/hero.avif
ffmpeg -y -i .fallback-frames/hero/f0031.png -vf crop=1280:720 -frames:v 1 \
  -c:v mjpeg -q:v 5 public/fallback/hero.jpg
# graph: capture frame f0000 (resting constellation), scale=-2:720 instead of crop
```

The VP9 budget loop is two-pass CRF stepping +2 from 40 until the file fits
1460 KiB (`hero`: 40 → 5268 KB ... 56 → 1487 KB → 58 → 1195 KB ✓). Hero frames
are cropped center-1280x720 from the 1280x764 hero band; graph frames are
captured at deviceScaleFactor 2 (2304x1088) and scaled to 1524x720.

## Seam verification

Both loops were checked by decoding the finished WebM played twice
(`-stream_loop 1`) and comparing the frame pairs that straddle the wrap
against ordinary in-loop adjacent pairs (PSNR between decoded frames; higher =
more similar; `inf` = identical):

| pair                                   | hero      | graph     |
| -------------------------------------- | --------- | --------- |
| wrap: last frame → first frame         | 31.1 dB   | 44.3 dB   |
| baseline: adjacent mid-loop frames     | 31.3 dB   | 45.4 dB   |
| graph turnaround (frame 149 → 150)     | —         | 46.1 dB   |

The wrap-crossing difference is the same magnitude as normal frame-to-frame
motion in each video — i.e. the loop point is statistically indistinguishable
from any other frame step. Visual confirmation: the decoded last and first
frames are both the resolved knight (hero) / the same constellation pose one
drift-step apart (graph); landmark frames were also verified during capture
(f0000 knight at phase 0, f0130 resolved "VS" at 5417 ms, f0240 resolved
wireframe at 10 000 ms), proving the phase alignment that the loop math
depends on.

## App-code change (capture hook only)

One read-only URL-param hook in `src/islands/hero/HeroScene.tsx`, as permitted:
`?heroT0=<ms>` pins the hero's animation clock to `performance.now() - heroT0`
instead of the R3F clock (and derives `uTime` from the same value), so the
pipeline can start capture on an exact cycle boundary. Without the param —
i.e. for every real visitor — the code path is unchanged (`elapsedMs` and
`uTime` reduce to the identical `clock.elapsedTime` values). No other app code
was touched. (Housekeeping: `.fallback-frames/` added to `.gitignore`.)

The graph scene needed no hook: `window.__graphDebug` already exposes mount
state, and the ping-pong loop is phase-free.

## Known limitations

- Captured with SwiftShader (software GL). The 'full' tier renders 25 000 hero
  particles and the graph without visible bloom differences; output matches
  what this Chromium build presents, which is the same renderer class the
  no-WebGL2 audience would have seen anyway.
- VP9 at crf 58 softens the hero's individual particle sparkle (25k additive
  particles are essentially noise to a codec); shapes, colors and motion read
  correctly. If a larger budget is ever allowed, crf 48-52 (~3-4 MB) preserves
  the shimmer.
- The hero video bakes in the 1280-wide framing (particles roughly centered;
  the scene's right-of-center drift applies only to wider viewports).
